EA Explorer helper. Usage: {eax} <command> [options]
[ps1](.\eax is the launcher; the long form is: powershell -NoProfile -ExecutionPolicy Bypass -File .\eax.ps1 <command>)
[sh](On Windows: .\eax <command>)
[py](The launcher fetches uv into work/tools the first time and runs this Python program with it; D331)
First time: {eax} init, then {eax} up.   Every day: {eax} up to start, {eax} stop to stop (your data is kept).

## Start and stop
: cleanup, clean-restart and clean-run DELETE data. To stop without deleting anything, use stop.

### up|run [service...] [--wait-all]
> Starts EA Explorer. Keeps the databases, documents and settings from last time.
The everyday start; run is the same as up. It builds our images, pulls the others and starts in two tiers (D255):
the core first (sign-in, the database, the API and the screens; you can sign in when it says ready), then Reports,
Documents, draw.io and the sample data in the background. Before starting it copies what is new or changed in the
industry pack sources into library/industry-packs (packs auto; quick when nothing changed), and as it starts it loads
the packs and the documentation into Documents and the library, and prepares the test runner in the background
(everything you need, nothing to run by hand, D584). Afterwards it prints the addresses and, on a laptop, the logins.
  --wait-all     start everything and wait until all of it is up (also on debug, restart and the clean-* commands).
  service...     start only those services and what they need: "up api proxy" starts the database, the API and
                 nginx only (about 1 GB); the API is then at https://localhost/api/docs.
Running up on a running installation is an upgrade: everyone sees the maintenance page until it has finished.
$ {eax} up
$ {eax} up --wait-all
$ {eax} up api proxy

### stop|down
> Stops EA Explorer (removes the containers). Keeps all data: databases, documents, settings, backups.
Nothing is deleted: the Docker volumes and the work folder stay, so the next {eax} up carries on where you left off.
Use it before shutting the computer down, or to free memory. down is the same as stop.
$ {eax} stop

### restart [--wait-all]
> Stops EA Explorer and starts it again (stop, then up). Keeps all data.
Use it when something is stuck. Each step writes its own log. To start again with empty databases, use
clean-restart instead.
$ {eax} restart

### cleanup [--all] [--yes] [--certificate]
> Stops EA Explorer and DELETES the work folder (config, logs, backups); --all: the databases too.
Deletes: the config file, every log, the laptop data folders, and every backup and restore log. With --all it also
deletes the Docker volumes, so the databases and documents start empty. Keeps: the local certificate
(work/data/tls; --certificate deletes it too) and work/tools. Asks you to type yes unless --yes is given.
$ {eax} cleanup
$ {eax} cleanup --all

### clean-restart [laptop|server] [--wait-all]
> Stops EA Explorer, DELETES everything (databases included) and starts fresh. Does not ask.
For testing a new version: stop (down), then cleanup --all --yes, init and up. Fetches the current base images first
(with their security fixes) and rebuilds our images on them, then starts with empty databases and the sample data, the
industry packs, the documentation and (in the background) the test runner: nothing else to run before testing. The
trusted certificate and persist/ are kept.
$ {eax} clean-restart
$ {eax} clean-restart --wait-all

### clean-run [laptop|server] [--wait-all]
> DELETES everything (databases included), then starts fresh: cleanup --all, init, up. Does not ask.
Like clean-restart, it fetches the current base images first and rebuilds our images on them.
$ {eax} clean-run
$ {eax} clean-run server

### maintenance on|off
> Shows (or stops showing) the maintenance page to everyone.
Served by the proxy. Restores and up (an upgrade) switch it on and off themselves.
$ {eax} maintenance on
$ {eax} maintenance off

## Status and logs

### status
> Lists every container with its state and health, then the disks. Changes nothing.
First the release and its build ("EA Explorer 1.0.0, build 4f2a9c1", as at the top left of the screens). Stopped
containers are listed too. Then the file systems: Docker's disk, the work and backups folders, and this
computer's drive (size, used, free).
$ {eax} status

### url
> Prints the addresses to open (and the logins on a laptop).

### logins
> Prints every user name and password (laptop only).

### logs [service|backup|clean] [--older-than N] [--yes]
> Follows the logs of every container, or of one; or backs up or cleans the logs kept on disk.
Ctrl+C stops following; nothing is stopped. Every container's log is also kept on disk, one file a day (logs/, or the
folder EAX_LOGS_DIR names), across clean-restart and updates (R2.32). `logs backup [tag]` zips those and eax's own
logs (work/logs) into work/backups/logs; `logs clean` deletes them and the log backups when older than N days (default
14 on a laptop, 90 on a server; also every night, System Admin > Settings "Delete logs older than"), asking first
(--yes skips it) (R2.30).
$ {eax} logs
$ {eax} logs api
$ {eax} logs backup before-upgrade
$ {eax} logs clean --older-than 30 --yes

### diag
> Saves a diagnostics report into this run's log: the file to send when asking for help.
Docker versions, memory and disk, image settings, every container's state, the last 300 log lines of each
container, and the compose configuration (passwords masked).
$ {eax} diag

### footprint [label] | --watch [minutes] [label]
> Measures how much each container takes and keeps it in work/footprint, beside the measurement before.
Image size, the container's own disk, its volumes, memory and CPU now, and how long it took to start (to healthy).
work/footprint/latest.md is the table, with the change since the one before in brackets: measure before and after a
change (label says which). Also System Admin > Footprint (R2.22). Changes nothing.
--watch samples every container's memory every 15 seconds (10 minutes unless given): each one's lowest, average and
peak, the whole installation's peak beside the guide of 10 GB (EAX_MEMORY_TARGET_MB; not a limit) and whether the
Docker host paged (swap). Kept in work/footprint/latest-memory.md. Every self-test run is watched the same way on its
own (memory.md in its folder). Release 3.5 (R3.5-M1).
$ {eax} footprint
$ {eax} footprint after-slim-images
$ {eax} footprint --watch 30 at-rest


### measure [--restart|--clean-restart] [--full] [--unattended] [--use-minutes N] [--from N] [--yes]
> Measures how much memory EA Explorer needs, in one go: each step run and checked, then a summary.
Steps: a restart (only when asked), memory while it starts and loads (20 minutes), a snapshot, the smoke test, at rest
(10 minutes), in use (20 minutes; on a laptop the browser opens for you to use it), the full test while you use it,
then one summary: each situation's peak and average, paging and the biggest containers, beside the guide of 10 GB
(not a limit). Kept in work/footprint/measure-<time>.md. Safe on a running installation and on servers:
--clean-restart (DELETES everything) is refused except on a laptop, and on a server the full test runs only with
--full (its restore part asked first). --unattended: nobody there (no browser; no in-use step on a laptop). A step
that fails stops it with the command to carry on (--from N). Release 3.5 (R3.5-M1).
$ {eax} measure --clean-restart
$ {eax} measure
$ {eax} measure --from 4 --yes
### databases
> Lists every database EA Explorer uses: what it holds, where it lives and whether it answers.
Each has its own setting in work/eaexplorer.env: empty = the shared PostgreSQL; set one to move that database to a
container or server of its own (docs/databases.md). Also System Admin > Databases (R2.50).
A database of its own gets its tables at the next start (eax up). `copy tests` brings the self-test runs made
before it moved (R2.28). `speed` times how the database compares text, and lists where the code does (R2.52).
$ {eax} databases
$ {eax} databases copy tests
$ {eax} databases copy operations
$ {eax} databases speed

### persist [list|delete] [<item>] [--all] [--yes]
> Lists what persist/ holds, or deletes an item of it (or everything) for good.
persist/ survives every reset by design: the schedules, the banner, the Self-test settings, the safety backups taken
before a command that deletes everything, the reset-survival results. A deleted settings file falls back to its
default (no schedules, no banner). Asks you to type DELETE (--yes skips it). Also System Admin > Persist (R2.26).
$ {eax} persist
$ {eax} persist delete banner.json
$ {eax} persist delete --all --yes

## Backups and restores

### backup [tag]
> Takes an infrastructure backup now: every database, the document files, the certificate and config.
Also the release and image versions. Into work/backups/infrastructure (D216, D226).
$ {eax} backup
$ {eax} backup before-upgrade

### backups [words]
> Lists every backup (infrastructure and application); with words, only the ones that match.
Words are looked for in the tag, name and maker.
$ {eax} backups
$ {eax} backups before-upgrade

### restore [name|tag|latest] [--what full|app|app+data|db|files] [--yes]
> Restores an infrastructure backup. Asks what to restore, then for RESTORE to confirm.
Unless --yes is given. By name, by tag (the newest with it) or latest (the newest good one); without one it lists them to choose from.
  full       everything
  app        the config file
  app+data   the config file, the repository and document databases and the document files
  db         every database
  files      the document files and the certificate
A backup of the current state is taken first; nothing live changes until all is restored cleanly; it can be run
again. Works when the console is down (starts db, backup and ops).
$ {eax} restore latest
$ {eax} restore before-upgrade --what db

### restores
> Lists every restore (infrastructure and model) with its status.

### restore-log <id>
> Shows a restore's whole log (also in work/backups/restores/<id>).
$ {eax} restore-log 12

### delete-backup <name>
> Deletes an infrastructure backup (unpin it first if it is pinned).

### delete-restore <id>
> Forgets a finished restore and its log.

### stop-backup
> Stops the backups running; the partial backup is deleted. A restore cannot be stopped.
Infrastructure backups stop at once; application backups after the model they are on.

### app-backup [tag]
> Backs up every model now (an application backup), into work/backups/application.
$ {eax} app-backup month-end

### restore-model
> Restores one model from an application backup, as a new model or over itself.
Lists the backups and the models in them to choose from. Needs the api container running.

### restore-app [run|tag|latest] [--yes]
> Restores every model of an application backup, each over itself (each backed up first).
Models no longer there are made again; newer models stay as they are. Needs the api container running.
$ {eax} restore-app latest

### schedule [list|add <name> [when] [--off] [--no-backup] [--keep N] [--banner] [--confirm <name>] -- <command>|demo-reset [--at HH:MM] --confirm <name>|on|off|remove|run <id>]
> Scheduled eax commands: a cron in the platform, e.g. a demo that resets itself every night.
The same schedules as System admin > Command centre > Schedules, kept in persist/schedules.json, which no reset
deletes (D558, D559); the operations helper starts what is due, in the installation's time zone (EAX_TIMEZONE). When:
--at HH:MM (every night, the default), --weekly <0-6> (0 Sunday) with --at, --hourly <minute>, --once
YYYY-MM-DDTHH:MM or --cron "<minute hour day month weekday>". A command that deletes everything (clean-restart,
clean-run, cleanup) needs --confirm with the installation's name, once; it takes a safety backup first unless
--no-backup (the newest --keep N, default 3, kept in persist/safety-backups/). --banner tells everyone when the demo
resets. A run missed while the machine was off runs once if found within the hour; one due while another command runs
waits up to 30 minutes. Every run is in the Command centre's History.
$ {eax} schedule list
$ {eax} schedule add "Nightly backup" --at 01:30 -- backup nightly
$ {eax} schedule add "Weekly smoke test" --weekly 1 --at 06:00 -- test smoke
$ {eax} schedule demo-reset --at 02:00 --confirm demo-laptop
$ {eax} schedule off a1b2c3

## Updates

### update [--status] [--retry] [--channel prod|rc|latest] [--to <version>] [--at <time>] [--url <link>] [--yes]
> Moves to a newer release from the git repository: a full backup first, then one release at a time.
Without options it is guided: it shows the installed version and the channels, lists the versions above the installed
one (forward only) with their release notes, and asks which one, now or at a time, and to type YES. Prod (tags vX.Y.Z
on the release branch) is always offered; RC (tags vX.Y.Z-rc.N) and Latest (every commit on main) only once enabled in
System admin > Updates. First a full backup (every database, every file, the config file and the code as it is, local
changes included; pinned), then the maintenance page while each release on the way is built here, started and checked.
A failed step stops and asks: --retry runs it again, or roll back. The update runs in its own updater container, so it
carries on while EA Explorer restarts. --status shows the installed version, the update running, the schedule and the
history. --url sets the repository link (EAX_UPDATE_GIT_URL). --at 22:00 (or a date and time) schedules it; signed-in
people see a banner beforehand. Also on System admin > Updates (Super Admins and IT Admins).
$ {eax} update
$ {eax} update --status
$ {eax} update --channel prod --to 0.20.0 --at 22:00
$ {eax} update --retry

### rollback [--yes]
> Back to the version before the last update: its code and its pre-update backup put back.
Work done since the update is lost; the current state is backed up first and kept. The failed version is marked in the
history. Asks you to type YES unless --yes is given.
$ {eax} rollback

### packs [auto|source [folder...] [--clear]|load [folder]|reload|status|collect [source...]]
> The industry packs: the books, workbooks, metamodel Excel and PowerPoints on the library's Pack tab.
Nothing to run by hand (D584): every up, run, restart, clean-restart and clean-run copies what is new or changed in the
pack sources into library/industry-packs first (packs auto; quick when nothing changed; nothing to do when no source
folder is there), and EA Explorer puts them into Documents as it starts (new or changed files only, by checksum; files
marked not for AI use are never loaded; the start-up status shows "Industry packs loading n of N"). The pack sources:
persist/settings.json (set with packs source, kept across resets), else EAX_PACKS_SOURCE in the config (several
separated by ;), else Enterprise_Architecture\Industry Specific Guidance and Sample_Repo (the metamodels and views) in
your home folder. collect (optional) copies them now; the "complete set" zips are opened, the same file kept once,
files over 50 MB split into parts below 45 MB (no Git LFS). load (or reload) puts them into Documents now; load
<folder> loads another folder on this computer. status shows each industry's pack. See docs/industry-packs.md.
$ {eax} packs status
$ {eax} packs source "D:\Packs\Industry Specific Guidance" "D:\Packs\Sample_Repo"
$ {eax} packs source --clear
$ {eax} packs load "D:\More packs"

### import [source|--all] [--as user]
> Takes the files other systems dropped in their delivery folders; each waits for review in the screens.
Without a source it lists every import source (a model's Import and export tab > Deliveries), its folder and how many
deliveries wait. With a source (its name, folder or id) or --all it takes the files in the source's folder in the
API's import folder, deliveries/<model>/<source>/incoming (the eax-imports volume, or EAX_IMPORT_DIR, which IT may map
to SFTP or a share). A CSV set with master.csv becomes one delivery; each workbook, .zip or CSV one each. Each is
previewed, then a Committer accepts or declines it on the model's Deliveries tab. --as names who took them (the log).
Needs the api container running. The formats: docs/import-formats.md.
$ {eax} import
$ {eax} import "Configuration database"
$ {eax} import --all

## Test

### check
> Checks that Docker is running and the config and compose files are valid. Starts nothing.
$ {eax} check

### test [smoke|full|backup|restore|ui-review|failed [run] [--warnings]|watch [run] [--log]|stop [run]|api <method> <path>|delete <run|all> [--older-than DAYS]|clean] [--yes]
> Test this installation: smoke or full; only what failed last time; or delete the test data.
The same two tests as System Admin > Tools > Self-test (owner, 12 Nov 2026, D592: "Smoke or Full. Not too many
options"); a run started in either place shows in both. Each run first removes any test data earlier runs left
(D593), starts a test container of its own, makes the models, project and test accounts it needs
(self_test_<id>_<n>), tests only inside them, writes the report and removes the container. Nothing else changes.
It prepares the test container first (seconds when it is current; the first time 5 to 15 minutes). Super Admins
and IT Admins.
  smoke   (the default) a few minutes: every role signs in, every main area answers, every page opens and the key
          journeys run once.
  full    everything: every API endpoint as every role (allowed and refused), the database checks, security, then
          every page and every journey in a headless browser, the backup checks, and last the restore test below
          (asked first; --yes skips the question; without a terminal and without --yes it is left out).
  backup  only the backup checks (the last part of full): an infrastructure and an application backup, each restored into
          a scratch copy and counted, then removed; nothing live is touched (R2.45). Until they pass, the Backups page shows
          these commands instead of its buttons (R2.46)
  restore  the full backup-and-restore test, on this installation (R3.8): the run's content fingerprinted, an
          infrastructure backup (also the safety backup) and an application backup made, the content changed, then
          restore all, one model over itself and each part of the infrastructure backup (db, app+data, files, full)
          restored in turn and the content compared each time; signing in checked after each; the backups it made
          removed; when a step fails the safety backup is put back whole. It stops the services while a restore runs
          and takes as long as it takes. Asks first (--yes skips that). The command line only, never from the web.
  ui-review  screenshots of every main page as each test role at laptop, large and narrow widths, with notes (page
          wider than the window, missing titles, unnamed buttons and fields, long text); ui-review.html in the run's
          folder. It changes nothing: the notes are discussed before any fix (R2.12)
  failed  only the checks that failed in the last finished run (or in the run named: failed 12), as the same roles,
          in fresh test data; --warnings repeats its warnings too. Quicker while fixing; the report shows each check
          then and now, and when all pass the earlier run is marked as followed up. A full run is still what counts
          for a release. Also Self-test > History > Run the failed ones again (R2.36).
  watch   follow a run as it happens, from a second terminal (R3.2): the step running now (what it checks), each
          check as it is recorded with its outcome, each failure with its reason, and the counts at the end; --log
          adds the run's log lines. The run going on, else the run named (watch 12), else the last one. Ctrl+C stops
          watching, not the run. The same as Self-test > a run > Watch on the web.
  stop    stop the run going on (or the run named: stop 12): it ends at its next step and removes its test data, as
          the Stop button on the Self-test page.
  api     one call through the API test harness (R3.16): eax test api GET /api/v1/models/{model} --as architect, or
          a write with --body '{"name": "x"}'. It runs in a harness session's own test data (the newest of the last
          20 hours, or a new one): {model}, {project} and {entity} are filled from it; reads go anywhere, writes only
          into test data. Prints the status, the time and the answer, and the same call as a curl line. The same as
          Self-test > API harness on the web, where calls can be saved as cases the self-test then runs too.
  delete  deletes test runs for good: their test data, results and screenshots, reports, logs and videos (R2.43):
          delete 12, delete all, delete --older-than 30; asks you to type DELETE (--yes skips that). Old runs also go
          by themselves after the days set on the Self-test page (default 30)
  clean   deletes the test data of every run, for good (asks you to type DELETE; --yes skips that). The reports stay.
          --dry-run lists what it would delete (models with their counts, projects, accounts) and deletes nothing.
          Each run removes its own test data when it ends (passed, failed or stopped); lists leave test data out.
A run can start right after up or clean-restart: it waits only for the services it tests (up to 10 minutes), never
for the sample data or the industry packs; a switched-off service's checks are skipped.
The report: work/tests/<run>/report.html (and the Self-test page's History). The exit code is 1 when a test failed.
$ {eax} test
$ {eax} test full
$ {eax} test backup
$ {eax} test restore
$ {eax} test api GET /api/v1/models --as architect
$ {eax} test watch
$ {eax} test stop 12
$ {eax} test ui-review
$ {eax} test failed
$ {eax} test failed 12 --warnings
$ {eax} test delete --older-than 30
$ {eax} test clean
$ {eax} test clean --dry-run

## Settings and services

### services
> Lists the optional services, whether each is on in the config file, and its containers' state.
The optional services: reports, documents, drawio, mcp, change_log, backups, library, views.

### service <name> on|off
> Switches one optional service on or off, then starts or stops its containers.
It keeps a dated copy of the config file in work/config-history first. Everything is on unless switched off
(D191). Also in System admin > System settings > Services.
$ {eax} service reports off
$ {eax} service reports on

### servers [n]
> Shows how many API and job servers run; with n (1 to 16), sets the number without a restart.
With n it writes EAX_API_SERVERS (a dated copy of the config file first) and adds or removes servers now; nginx
spreads the API calls across them (D249). Also on Administration > Containers.
$ {eax} servers
$ {eax} servers 3

### standby [status|promote]
> The database standby (EAX_COMPOSE_EXTRA=standby): how far behind it is, or make it the primary.
With EAX_COMPOSE_EXTRA=standby and EAX_REPLICATION_PASSWORD in the config file, db-standby follows the primary
continuously (phase 36.3, D527). status shows the primary's replication and how far behind the standby is. promote
makes the standby the primary after the primary is lost (it asks you to type PROMOTE); then set EAX_DB_HOST to it
and run {eax} up. A standby is not a backup: the nightly backups stay.
$ {eax} standby
$ {eax} standby promote

### secrets [show|push|pull] [--to|--from provider:name]
> Keeps the passwords in a key vault (a file, AWS, Azure) or takes them back from it.
The passwords and keys in work/eaexplorer.env can be kept in a key vault as well (D504): file:<path> (a file outside
the installation, readable by its owner only; also on a DigitalOcean Droplet), aws:<secret name> (Secrets Manager,
one secret holding them all) or azure:<vault name> (Key Vault, one secret each). The config file says which
(EAX_SECRETS_FROM). Docker Compose still reads them from the config file when it starts.
  show           where they are kept (the default).
  push           the config file's values into the vault (eax deploy does this once when you choose a vault).
  pull           the vault's values into the config file (a dated copy of the file first, in work/config-history),
                 e.g. after rebuilding the server or rotating a password; then restart.
$ {eax} secrets
$ {eax} secrets push --to aws:eaexplorer/prod
$ {eax} secrets pull

### trust [--remove]
> Makes the browser trust EA Explorer's local certificate (no more warnings on https://localhost).
[win]It adds work/data/tls/ca.crt to your Windows trusted root certificates.
[unix]It adds work/data/tls/ca.crt to this computer's trusted certificates (macOS: your login keychain; Linux: it
[unix]prints the commands, which need sudo).
Run it once after the first start: clean-run and clean-restart keep the certificate. --remove takes EA Explorer's
certificates out again.
$ {eax} trust
$ {eax} trust --remove

## Site and deploy

### init [laptop|server]
> Creates the config file work/eaexplorer.env and the work folders. Never overwrites a config file.
Made from the template for the deployment kind (laptop if not given). Nothing is generated: on a laptop every
password is P^55w0rd1234&; on a server, replace every change-me value in work/eaexplorer.env before starting.
A server asks for the folder for backups (a mounted network share or volume, EAX_BACKUP_DIR): no backups are
taken until it is given (R2.44). A laptop keeps them in work/backups.
$ {eax} init
$ {eax} init server

### deploy [--console|--web] [--kind laptop|server|aws|azure|digitalocean] [--plan] [--yes]
> Guided deployment: this laptop, a server (here or over SSH), AWS, Azure or DigitalOcean.
The deployment wizard (D498). It first asks whether to carry on here in the console or in a web page it opens in your
browser (served by eax itself, before EA Explorer is up); --console or --web skip that question. Then it asks where:
  laptop         this computer: makes the config file if there is none, starts EA Explorer, checks it is healthy.
  server         a Linux server: this one, or another one over SSH from here (a user who may use sudo, signed in
                 with your SSH key). Docker is installed if it is missing; the release is downloaded onto it.
  aws, azure, digitalocean
                 creates the machine from your cloud credentials (the aws, az or doctl command must be installed
                 here): the machine, a data disk, the firewall, a fixed address, storage for off-site backups, the
                 DNS names; or uses a machine you already have, over SSH.
For a server or a cloud machine it makes the config file with every password generated, your certificate or a
self-signed one, starts EA Explorer, checks it is healthy and shows the address and the first sign-in. It can also
keep the passwords in a key vault (see secrets) and move an existing installation there from one of its
infrastructure backups. Every step is in work/logs/eax-<time>-deploy.log (passwords masked); a step that fails
asks: retry, back to the answers, or quit. Cloud credentials are used for this run only unless you ask to keep them.
  --plan         show every step and every command it would run, and run nothing.
  --kind K       answer the first question; --answers file.json or --set key=value answer others (the answers'
                 names are shown before it starts); --yes runs without asking (every answer given or default).
Not set up yet? The installer downloads EA Explorer first and then runs this: see docs/deployment.md.
$ {eax} deploy
$ {eax} deploy --web
$ {eax} deploy --console --kind aws --plan

### console [--server https://host] [--insecure]
> A numbered menu for getting EA Explorer back up, for anyone (D330).
Status, start, restart, stop, problems and logs, back up, restore (guided), reset a password (a person,
Keycloak's administrator, break-glass, the database logins), users and roles, settings and switches, background
tasks, health and data quality, the maintenance page, a diagnostics file, and a prompt for every eax command. On
this machine nobody signs in; anything that changes or replaces data asks you to type YES. With --server it works
on another installation through its API (sign in with Keycloak, your roles).
$ {eax} console
$ {eax} console --server https://ea.example.org

## Developer

### debug [service...] [--wait-all]
> Starts like up but does not stop on a failure, then records the containers' output until Ctrl+C.
It saves a diagnostics report, then keeps recording every container's output to
work/logs/containers-<date-time>.log. The containers keep running after Ctrl+C. "debug api" starts and records
the API (and PostgreSQL) only.
$ {eax} debug
$ {eax} debug api

### clean-debug [laptop|server] [--wait-all]
> The same as clean-run, but ends with debug instead of up. Does not ask.

## Help and documentation

### help [command|--all]
> This overview; one command in full, with examples; or --all for every command in full.
Also: {eax} <command> --help (or -h, or /?).
$ {eax} help stop
$ {eax} help --all

### screen
> A full-screen eax in the style of Turbo Pascal: menus, a dialog per command, a live dashboard.
Also what {eax} with no command opens on a terminal (piped or in a script it prints this overview, as before). The
menu bar has the groups below: F10 or Alt and a group's letter opens one, the arrows move, Enter picks, Escape closes;
the mouse works too. A command's dialog is made from this help: choices as lists (or type one), flags as tick boxes,
values as fields, and the whole command is shown as you fill it; Run or Cancel. The middle of the screen shows each
container in its state's colour and the free disk space, refreshed every 5 seconds. A command that only prints (status,
backups, services, ...) shows its output in a window; one that asks questions or follows logs switches to the plain
terminal and comes back with Enter (Alt+F5 shows that screen too). F1 Help, F5 Refresh, Alt+X Exit. Textual is
fetched once into work/tools/pylib (nothing installed elsewhere); offline the first time, in an old console, or with
EAX_SCREEN=off in the environment, the numbered menu opens instead (R3.1).
$ {eax}
$ {eax} screen

### menu
> A numbered menu of every command by group: pick one, answer its questions, see it, then run it.
What {eax} screen falls back to when the full screen cannot open. Each option of the command is asked for in turn;
Enter leaves an optional one out. The whole command is shown before it runs, and it runs only when you answer y. Typing
a command that does not exist shows the nearest ones (did you mean).
$ {eax} menu

### document [--console|--web]
> Every command in full, with examples: in the console (page by page) or as a web page in your browser.
Asks which unless --console or --web is given. The web page is made from the same help, as one file with nothing to
download: work/docs/eax-commands.html (contents, search, the commands that delete data marked). In the console:
choose a group by number, search by a word with s, q to quit; Enter shows the next page.
$ {eax} document
$ {eax} document --web
$ {eax} document --console

@footer
Colours: in a terminal, status shows each container in its state's colour (green up, yellow starting, red down or
failing, grey a finished set-up step) and errors, warnings and headings are coloured. --no-color, NO_COLOR=1 or CI=1
turn colours off; output sent to a file or another program is always plain.
{eax} help <command> shows one command in full, with examples. {eax} help --all shows every command in full.
Every command and the console in detail: docs/command-line-and-console.md.
Logs: every command except help and cleanup writes its full output to work/logs/eax-<date-time>-<command>.log.
When a Docker step fails, a diagnostics report is added to that log, so the log is all you need to send.
